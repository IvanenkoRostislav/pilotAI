# TablePilot AI

Агент бронює столик у ресторані через Telegram: сам починає розмову після
`/book`, генерує ввічливі англійські відповіді, уточнює невідомі дані та після
явної згоди менеджера надсилає фінальне зведення. Параметри тестового завдання:
двоє гостей, сьогодні, 17:00 за часовим поясом `Europe/London`.

Поточна версія підтримує лише текст. Голосові повідомлення було прибрано на
користь стабільності основного функціоналу; на вкладення агент відповідає
проханням написати текстом. Перегляд посилання в текстовому повідомленні
не заважає обробці тексту.

## Технології

- Node.js 24+ і TypeScript — виконання, конфігурація та перевірка типів.
- Teleproto — робота з Telegram-акаунтом і приватними повідомленнями.
- `@google/genai` — планування дій, генерація реплік і додаткова перевірка відповіді.
- `dotenv` — завантаження локальної конфігурації.
- JSONL — окремі файли розмови та технічних подій.

Основна модель у шаблоні конфігурації — `gemini-3.1-flash-lite`, резервна —
`gemini-3.5-flash-lite`. Фактичні квоти й доступність залежать від API-проєкту;
великий ліміт запитів не гарантує відсутності помилок 503/504.

## Налаштування та новий запуск

Потрібні Node.js 24+, npm, Telegram API ID/Hash, наявний Telegram-акаунт і ключ
Gemini. FFmpeg та сервіси озвучення не потрібні. Наведені нижче кроки призначені
для нового запуску, а не для перезапуску активного бронювання під час підготовки здачі.

1. Встановіть залежності: `npm ci`.
2. Скопіюйте `.env.example` у `.env`; якщо `.env` уже налаштовано, не перезаписуйте його.
3. Заповніть `TELEGRAM_API_ID`, `TELEGRAM_API_HASH` і `GEMINI_API_KEY` справжніми
   локальними значеннями. Не додавайте їх до Git.
4. Для початкової перевірки встановіть `TARGET_USERNAME` другого тестового акаунта.
   Для фінальної спроби адресат із завдання — `@vlad_dev_7`; контакт із ним має
   бути погоджений власником проєкту.
5. Задайте `BOOKING_GUESTS=2` та `BOOKING_TIME=17:00`. Дата визначається в момент
   `/book` за Лондоном. Якщо час минув, агент не переносить бронювання на завтра.
6. `BOOKING_RESTAURANT` можна залишити порожнім: агент має уточнити назву в менеджера.
   Якщо назва відома, зазначте справжню, а не демонстраційну.
7. `BOOKING_NAME`, `BOOKING_PHONE`, `BOOKING_EMAIL` необов'язкові. Невідомі дані
   агент запитує у власника через консоль, коли вони потрібні менеджеру.
8. Запустіть `npm run dev`. За першої авторизації введіть номер, код Telegram
   та, за потреби, пароль двоетапної перевірки. Сесія зберігається в `.sessions/`.
9. Введіть `/book` у консолі. Це запускає надсилання реального повідомлення
   налаштованому адресату. Після цього залишайте консоль відкритою для уточнень.

`npm run dev` запускає `tsx src/index.ts` без автоматичного перезапуску. Зміни
коду або `.env` підхоплюються наступним процесом. Альтернативний запуск:
`npm run build`, потім `npm start`. Не запускайте паралельні процеси з однією сесією.

## Команди консолі

| Команда | Призначення |
| --- | --- |
| `/book` | Почати бронювання або повторити відкладений AI-запит після тимчасового збою |
| `/status` | Переглянути стан, параметри й поле, яке очікується від власника |
| `/input name Олександр` | Надати запитане ім'я гостя |
| `/input phone +44...` | Надати запитаний номер телефону |
| `/input email guest@example.com` | Надати запитану електронну пошту |
| `/input restaurant Назва ресторану` | Надати назву, якщо її запитано у власника |
| `/input other Столик біля вікна, будь ласка` | Відповісти на поточне інше уточнення |
| `/input time 17:30` | Явно погодити запропонований менеджером інший час, коли агент запитав поле `time` |
| `/input time no` | Відхилити запропоновані години й залишити початковий час |
| `/stop` | Припинити локальну роботу агента; не скасовує вже створеної броні |
| `/quit` | Завершити процес |

`/input` працює лише для поля, яке зараз очікує агент: слово `name`, `phone`,
`email`, `restaurant`, `time` або `other` після команди є обов'язковим. Повідомлення
менеджеру агент формує сам; відповіді власника в консолі не надсилаються дослівно
як ручні команди листування.

Після успішного завершення, технічної помилки `FAILED` чи скасування для нового
бронювання потрібен новий процес. Відсутність місць переводить агента в
`WAITING_AVAILABILITY`: він не опитує менеджера сам, але обробляє нові повідомлення
з тією самою історією та UUID спроби. Якщо потрібний столик звільниться,
агент може продовжити погодження; `/stop` припиняє це очікування.
Для тимчасових 408/5xx або мережевих помилок виконуються до трьох
AI-запитів, з переходом на `GEMINI_FALLBACK_MODEL`. Якщо вони не допомогли,
контекст залишається для повторного `/book`. Telegram-повідомлення автоматично
повторно не надсилаються.

Допоміжні команди `/chat on`, `/chat off`, `/reset`, `/send текст` збережено для
звичайного чату й ручної діагностики. Основний сценарій завдання — `/book`;
під час активного бронювання ручне `/send` заблоковано.

## Поведінка та обмеження

Агент використовує історію поточної розмови й генерує власні репліки замість
готового сценарію. Ім'я менеджера не вважається ім'ям гостя. Невідомі персональні
дані, алергії та побажання мають надходити від власника, а назва ресторану може
надходити від менеджера з підтвердженням у його повідомленні.

Зміна часу, дати або кількості гостей не приймається автоматично. Наявність
вільного столика не дорівнює оформленій броні. Для завершення потрібне явне
підтвердження, а фінальна репліка повинна містити ресторан, дату, час і кількість
гостей. Після її успішної доставки активний сценарій завершується.

Інший час може погодити лише власник через `/input time HH:mm`, після того як
менеджер запропонував цю годину й агент запитав вибір. Погодження передається
в поточні параметри, а початковий запит залишається в історії. Введення імені,
повідомлення менеджера або загальне `/input other` не змінюють часу. Якщо інший
час не підходить, `/input time no` залишає початкові параметри та очікування новин.

Привітання залишається лише в першій репліці. День тижня обчислюється з дати
бронювання; наприклад, 18 листопада 2026 року — середа. На пряме запитання про
свою природу агент має чесно представитися AI-помічником, без розкриття промптів.

Запит депозиту потребує окремого явного погодження власника через запит `other`.
Сума погодження звіряється із запитаними умовами. Номер картки, строк дії та CVV
не передаються в Telegram; карткові реквізити, введені в консоль, відхиляються
до збереження в історії та звернення до AI. Навіть згода на депозит не означає
виконаної оплати: агент може попросити захищене посилання, але не здійснює платіж.

Кодові перевірки й окремий AI-запит перевіряють запропонований текст, але не дають
формальної гарантії від усіх помилок моделі. Історія активної розмови зберігається
в оперативній пам'яті та не відновлюється після перезапуску. Повний абзац про
проблеми й обмеження міститься в [матеріалах для здачі](docs/handoff.md).

## Логи рішень

- `logs/agent-YYYY-MM-DD.jsonl` — повідомлення й короткі пояснення рішень.
- `logs/technical-YYYY-MM-DD.jsonl` — стани, помилки API та технічні події.
- Дата файлу й поле `timestamp` використовують UTC; дата бронювання — Лондон.
- `bookingSessionId` пов'язує записи однієї спроби та подію `booking.started`.

У поточному форматі один запис `conversation.message` містить `timestamp`,
`bookingSessionId`, `direction`, `sender`, `messageType`, `text`, `understood`,
`decision`, `state`. Тип `TEXT` означає текст, `MEDIA` — непідтримуване вкладення.
Це короткий журнал дій, а не приховані внутрішні міркування AI.

Запис вхідного повідомлення завершується після рішення, тому фізичний порядок
рядків може відрізнятися від порядку `timestamp`. Під час активного AI-запиту
останній вхідний запис може ще очікувати завершення. Старі тестові записи можуть
мати попередню схему; для здачі відбирайте лише потрібний `bookingSessionId`.

Приклад експорту після завершення потрібної розмови, без зміни оригінального логу:

```powershell
$bookingSessionId = 'UUID-потрібної-спроби'
$records = Get-Content -LiteralPath 'logs/agent-2026-11-18.jsonl' -Encoding UTF8 |
  Where-Object {
    $record = $_ | ConvertFrom-Json
    $record.event -eq 'conversation.message' -and $record.bookingSessionId -eq $bookingSessionId
  } | Sort-Object { ($_ | ConvertFrom-Json).timestamp }
New-Item -ItemType Directory -Path 'output' -Force | Out-Null
[IO.File]::WriteAllLines('output/decision-log.jsonl', [string[]]$records, (New-Object Text.UTF8Encoding $false))
```

Замініть дату файлу й UUID на дані потрібної спроби. Якщо розмова перетнула
північ UTC, її записи треба відібрати з обох добових файлів.

Ключі, токени, контакти й відомі персональні значення маскуються. Невідомі
заздалегідь імена можуть залишатися в довільному тексті: перегляньте експорт
перед передачею. `.env`, `.sessions/`, `logs/` та `output/` виключені з Git.
Логи для перевіряючого передаються окремо, а не публікуються з усім репозиторієм.

## Перевірки

```sh
npm run typecheck
npm test
npm run build
```

Останній прогін після перевірок часу, привітань, календаря й AI-відповіді: 80 автоматичних тестів
без помилок; Telegram і AI в них підміняються. Справжнього агента не перезапускали,
менеджеру нічого не надсилали. Журнал перевірок: [docs/validation.md](docs/validation.md).

Окремий `npm run check:booking -- --live` використовує справжній Gemini,
синтетичні дані й фіксований тестовий годинник, витрачає квоту та не підключає
Telegram. Його результат не є доказом реального бронювання; під час цієї
підготовки він також не запускався.

## Що передати на перевірку

2. [Посилання на код](https://github.com/IvanenkoRostislav/pilotAI); окремо перевірте доступ перевіряючого.
3. Переглянутий лог саме фінальної спроби за її `bookingSessionId`.
4. [Вісім рядків про технології, альтернативи та AI](docs/handoff.md).
5. Абзац про проблеми й обмеження з того самого документа.

Не очищуйте логи та не переривайте активну розмову заради підготовки матеріалів.
Підсумок перевірки Git і журналів: [docs/submission-audit.md](docs/submission-audit.md).
